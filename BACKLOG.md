- [ ] **A burndown child can implement the wrong item, in the wrong repo, and the parent only finds out by accident** (c4po, added 2026-08-02) — Observed live during the 2026-08-02 burndown re-run. The child dispatched for "Verify Codex's current slash-command syntax" instead implemented **two unrelated backlog items** — it built the `/done` command and committed it to the workspace repo (`1bb21b2`), and separately committed a new rule file plus a `BACKLOG.md` entry to `repos/waiq` (`6cf8440`) — then declared the item it was actually given `INFEASIBLE`. Its prompt explicitly forbade editing any `BACKLOG.md` and told it to implement only the one item; it did both anyway. Two distinct gaps. (1) **Blast radius**: the child was dispatched at the workspace root with `--add-dir ${BORG_ROOT}`, and Codex's `.git` carveout is only `root + "/.git"`, so every nested `repos/*/.git` under that root stays writable — a workspace-scoped child can silently commit into any product repo. `.bin/run-scheduled-task.sh` grants each repo's `.git` deliberately, but nothing scopes a *child* to the repo its item belongs to. (2) **Verification**: `c4po/.claude/scheduled/c4po-backlog-burndown.prompt` → BURN tells the parent to check "the dispatch repo's `git log`" for the item's commits — singular repo, and it never says to check that the commits correspond to *this* item. Here the parent caught it only because the child's own transcript happened to echo an unexpected `git log -1`. Worth fixing both: scope a child's writable roots to its dispatch repo (plus the workspace only when the item genuinely spans it), and make the parent's verification step diff every repo it granted, against the item it dispatched, before checking anything off. Keeping the two commits was a judgement call — both were coherent, useful work — but the next one may not be.

- [ ] **Cerebruh's raw↔wiki citation join breaks on typographic apostrophes** (cerebruh, added 2026-08-02) — Found while measuring the Medium corpus for the evaluation above. Some filenames under `wikis/*/raw/` use a curly apostrophe (`’`) while the derived pages in `wikis/*/wiki/` cite the same source with an ASCII apostrophe (`'`), so any exact-string join between a raw source and the pages citing it silently undercounts. Concretely: the Medium scan matched 171 derived pages after normalizing apostrophes and only 159 without — **12 pages whose provenance link is invisible to a naive audit**. 15 raw filenames contain a curly apostrophe in total, so the blast radius is larger than the Medium subset that surfaced it. This is a provenance-integrity defect, not a cosmetic one: it means "which pages depend on this source?" — the question you ask when a source is retracted, superseded, or found wrong — returns an incomplete answer. Fix direction: decide whether to normalize apostrophes at ingest time (changing filenames, which breaks existing citations unless they are rewritten together) or to normalize at comparison time in `AUDITING.md`'s checks (safer, no rewrite, but every future consumer must remember). Then add an assertion to the audit that every `sources:` entry in a wiki page resolves to a file that actually exists under that sub-wiki's `raw/`, which would have caught this and would catch plain typos too. Note `cerebruh/` wiki content is read-only to agents, so any filename change has to run through Cerebruh's own ingest/audit workflow rather than being patched in place.
